## 1. Цель и границы

**Что делаем:** русскоязычный веб-сервис, где руководитель (тимлид, скрам-мастер, HR) создаёт команду, запускает опрос одного из типов, рассылает ссылку участникам и получает результаты на почту и в веб-интерфейсе.

**Типы опросов (MVP):**
1. **Движущие мотиваторы** (по методике Moving Motivators, Management 3.0) — основной продукт.
2. **Health Check команды** (по модели Squad Health Check, Spotify).

**Главная гипотеза MVP:** руководители готовы платить 299 ₽ за опрос команды больше 8 человек. Оплату в MVP **имитируем** (§7) и меряем, сколько людей нажимают «Оплатить».

**Принципы:**
- Вход без пароля — только по волшебной ссылке на email.
- Участнику регистрация не нужна: открыл ссылку → прошёл → готово. Mobile-first.
- Результат — заготовка для разговора (подсказки к обсуждению), а не просто отчёт.
- Данные хранятся в РФ (152-ФЗ): Coolify на VPS Timeweb Cloud (российский ДЦ).
- Только русский язык, но все строки UI — через словарь (i18n-ready).

**Вне MVP:** реальный приём платежей, PDF, SSO, интеграции (Slack/Telegram/Jira), конструктор опросников, Delegation Poker, eNPS, мобильные приложения, мультиязычность.

#### Механика прохождения

1. **Ранжирование (обязательно).** Участник упорядочивает 10 карточек от наименее важной к наиболее важной. Desktop — горизонтальный ряд `full`-карточек (слева «Менее важно» → справа «Более важно»), drag-and-drop. Mobile — вертикальный список `compact` (сверху «Более важно» → снизу «Менее важно»), drag-and-drop + кнопки ↑/↓ на плашке. Изначальный порядок — случайный (перемешивание на клиенте). Результат: `rank` 1..10 для каждой карточки (10 = самый важный).
2. **Оценка команды (обязательно, с версии методики 2).** Участник проходит по одному экрану на каждую карточку, в порядке своего ранжирования (самые важные сначала): «Насколько в вашей команде развит мотиватор „Принятие“?» — от 1 до 5 звёзд. У каждой оценки каждой карточки есть своё описание (`levels` в каталоге, 10 × 5 формулировок), чтобы все понимали шкалу одинаково. Перейти дальше без оценки нельзя. Оценки привязаны к ключу карточки и сохраняются при возврате к шагу 1. Шаг 1 спрашивает о личной важности, шаг 2 — о том, как обстоят дела в команде. Опросы, созданные на версии 1, проходятся без этого шага.
3. **Влияние изменений (опционально, включает организатор).** Организатор задаёт от 1 до 5 изменений (например: «Переход на новую оргструктуру с 1 января», «Возврат в офис 3 дня в неделю»). Участник проходит по одному экрану на каждое изменение: вверху текст изменения и «Изменение 2 из 3», ниже 10 карточек `compact` **в порядке его собственного ранжирования** (самые важные сверху; порядок здесь менять нельзя). Для каждой карточки: ↑ станет лучше / — не изменится / ↓ станет хуже. По умолчанию все «—». «Назад»/«Далее» между экранами, черновик в `localStorage`. Если участник вернулся к шагу 1 и поменял ранжирование — оценки и отметки влияния сохраняются (привязаны к ключу карточки, не к позиции).
4. **Комментарий (опционально).** До 1000 символов: «Если что-то хотите подсветить»

#### Результаты по команде

- Средний ранг каждой карточки; сортировка по нему.
- Распределение рангов: тепловая карта 10×10 (карточка × позиция, число людей).
- Топ-3 / анти-топ-3 команды.
- Развитость в команде: средняя оценка 1–5 по каждой карточке и распределение по звёздам; карточки идут по важности, важные и слабо развитые подсвечены. Тот же график, что у участника на экране «Спасибо», но по средним значениям команды: порядок важности по горизонтали, средняя развитость по высоте. Неанонимный режим — оценки каждого участника.
- Согласованность: стандартное отклонение ранга по карточке («команда единодушна» / «мнения сильно расходятся»).
- Если был шаг 2 — **по каждому изменению отдельно**: для каждой карточки счётчики ↑/—/↓ и «индекс влияния» = (↑ − ↓) / N ∈ [−1; 1]; итог изменения = средний индекс по карточкам, **взвешенный по важности** (вес карточки = средний ранг команды / 10).
- **Сравнение изменений:** матрица «изменение × карточка» с цветом ячейки по индексу (красный ← 0 → зелёный) + рейтинг изменений («Самое болезненное для команды», «Самое позитивное»).
- Неанонимный режим дополнительно: таблица «участник × карточка», индивидуальная раскладка каждого, по каждому изменению — кто что отметил.

#### Подсказки к обсуждению (статичные шаблоны, без ИИ)

- Для каждой карточки из топ-3 — 2–3 вопроса (справочник `discussionPrompts` в каталоге). Пример для «Свобода»: «Где сейчас вам не хватает самостоятельности?», «Какие согласования можно убрать?». Написать вопросы для всех 10 карточек.
- Если std ранга карточки > 2.5 — «Мнения разделились — обсудите, почему для одних это важно, а для других нет».
- Если индекс влияния карточки < −0.3 — «Изменение „{изменение}“ может ударить по мотиватору X».
- Если карточка из топ-3 команды имеет среднюю оценку развитости < 3 — подсказка с повышенным приоритетом: «„X“ — один из главных мотиваторов команды, но развит слабо».
- Если карточка из топ-3 команды получила индекс < −0.3 хотя бы в одном изменении — подсказка с повышенным приоритетом (первой): «Под угрозой один из главных мотиваторов команды».
- Если по изменению голоса по карточке разделились (≥30% ↑ и ≥30% ↓) — «Изменение воспринимается по-разному — обсудите, кому оно поможет, а кому помешает».

Пороги — в конфиге.

### 4.2. Health Check команды

10 категорий:

| key | Название | Отлично 🟢 | Плохо 🔴 |
|---|---|---|---|
| `delivery` | Лёгкость поставки | Выпускать изменения просто, безопасно и в основном автоматизировано | Выпуск — это боль, риск и куча ручной работы |
| `process` | Подходящий процесс | Наш процесс нам подходит и помогает | Процесс мешает и навязан снаружи |
| `tech_quality` | Качество кода | Мы гордимся кодом: он чистый, понятный, покрыт тестами | Технический долг растёт, код страшно трогать |
| `value` | Ценность | Мы поставляем то, что действительно нужно пользователям, и гордимся этим | Мы делаем что-то, но непонятно, кому и зачем |
| `speed` | Скорость | Мы делаем быстро, без задержек и долгих ожиданий | Мы постоянно застреваем, ждём и не успеваем |
| `mission` | Миссия | Мы понимаем, зачем существуем, и нас это вдохновляет | Мы не понимаем, зачем мы здесь и куда идём |
| `fun` | Удовольствие | Нам нравится работать вместе, атмосфера отличная | Скучно, тяжело, хочется уйти |
| `learning` | Обучение | Мы постоянно узнаём новое и растём | Нет времени учиться, мы стоим на месте |
| `support` | Поддержка | Мы всегда получаем помощь и поддержку, когда просим | Мы застреваем, потому что помощи не дождаться |
| `ownership` | Хозяева или пешки | Мы управляем своей судьбой и решаем, что и как делать | Мы пешки: от нас ничего не зависит |

Организатор может **отключить** любые категории (минимум 3 остаются). Кастомные категории — фаза 2.

**Прохождение:** на каждую категорию (одна на экран на мобиле, список на десктопе):
- Оценка: 🟢 Отлично (3) / 🟡 Есть проблемы (2) / 🔴 Плохо (1). Обязательно.
- Тренд: ↑ Улучшается / → Без изменений / ↓ Ухудшается. Обязательно.
- Комментарий: опционально, до 500 символов.

**Результаты:**
- По категории: распределение 🟢/🟡/🔴, средний балл (1–3), итоговый цвет (≥2.5 зелёный, ≥1.75 жёлтый, иначе красный — пороги в конфиге), преобладающий тренд.
- **История:** сетка «категория × волна» (как в модели Spotify) по всем закрытым HC команды + график среднего балла.
- Комментарии по категории.
- «Обсудите в первую очередь» — 2–3 категории с минимальным баллом и/или трендом ↓ у большинства.

## 5. Пользовательские сценарии

### 5.1. Вход организатора (magic link)

1. Пользователь вводит email на `/login` (и на лендинге — «Начать»).
2. Backend нормализует email (trim, lower), создаёт пользователя, если его нет, генерирует токен 32 байта (base64url), сохраняет **SHA-256 хеш**, TTL 15 минут, одноразовый. Письмо со ссылкой `https://{host}/auth/verify?token=...`.
3. Ответ на запрос всегда одинаковый («Если адрес корректный, мы отправили письмо»).
4. **Защита от сканеров ссылок** (корпоративные почтовые фильтры открывают ссылки): страница `/auth/verify` показывает кнопку «Войти», и только по нажатию фронт делает `POST /api/auth/verify`. GET-запрос токен не тратит.
5. Verify проверяет хеш, срок, неиспользованность → помечает использованным, `email_verified_at`, создаёт сессию, ставит cookie, редирект на `/app` или `returnUrl` (только относительные пути).
6. При первом входе — «Как к вам обращаться?» (имя, опционально) + обязательная галочка согласия с политикой ПДн и офертой (фиксируем версию и дату).
7. Сессия: cookie `__Host-session`, HttpOnly, Secure, SameSite=Lax, скользящий срок 30 дней. Таблица сессий (хеш id) — для «выйти со всех устройств».
8. Rate limit: 5 запросов ссылки на email в час, 20 на IP в час.

### 5.2. Создание команды

`/app/teams/new`: название (1–100 символов), **размер команды** (обязательно, 2–200; подсказка «Сколько человек будет проходить опросы»). Лимита на количество команд нет. Команду можно переименовать, изменить размер, архивировать, удалить (каскадно, подтверждение вводом названия).

### 5.3. Создание опроса

`/app/teams/{id}/surveys/new` — мастер на одном экране:
1. **Тип:** «Движущие мотиваторы» / «Health Check» + краткое описание и «Как проводить» (раскрывающийся блок).
2. **Название** (по умолчанию «{Тип} · {месяц год}»).
3. **Число участников** — предзаполнено размером команды, можно изменить для этого опроса (2–200). Рядом живой индикатор: «До 8 человек — бесплатно» / «Опрос для 12 человек — 299 ₽».
4. **Анонимность:**
   - *Анонимный* — участники не представляются, индивидуальные ответы организатору не видны, только сводные результаты (с первого ответа, порога нет).
   - *С именами* — участник вводит имя. Организатор видит индивидуальные ответы. Участнику явно сказано: «Руководитель увидит ваши ответы под вашим именем».
   - Режим нельзя изменить после первого ответа.
5. **Специфично для типа:**
   - ММ: чекбокс «Оценить влияние изменений» → список: «+ Добавить изменение», текстовое поле (до 300 символов, обязательно), удаление, перетаскивание для порядка. От 1 до 5 (подсказка «Каждое изменение — ещё ~1 минута для участника»). После первого ответа список **заблокирован** (можно править только текст, без смены количества и порядка).
   - HC: список категорий с чекбоксами (все включены).
6. **Срок:** дата/время закрытия (по умолчанию +7 дней; часовой пояс пользователя, хранить UTC). Можно закрыть вручную раньше.
7. **Приветственное сообщение** участникам (опц., до 500 символов).
8. Кнопка: **«Запустить опрос»** (≤ 8 участников) или **«Перейти к оплате — 299 ₽»** (> 8) → §7.

После запуска — экран «Опрос запущен»:
- ссылка `https://{host}/s/{publicCode}` (10 символов base62, криптослучайный) + «Копировать»;
- QR-код (на клиенте);
- готовый текст приглашения для мессенджера.

### 5.4. Прохождение опроса участником

1. `/s/{code}` → приветствие: команда, тип опроса, сообщение организатора, режим анонимности (крупно), «займёт ~7 минут» (ММ) / «~5 минут» (HC), «Начать».
2. Неанонимный — поле «Ваше имя» (1–60 символов).
3. Шаги методики (§4), прогресс-бар, черновик в `localStorage`; на сервер — только финальная отправка.
4. Неанонимный — обязательное согласие на обработку ПДн перед отправкой.
5. После отправки — «Спасибо» + свой результат: ММ — график, где мотиваторы идут по порядку важности (слева менее важно, справа более), а высота показывает оценку развитости в команде; HC — свои оценки. Опросы методики v1 — раскладка `full`-карточками.
6. **Повторное прохождение:** клиент генерирует `respondentKey` (UUID) в `localStorage`; сервер хранит его хеш. Повторная отправка с тем же ключом, пока опрос открыт, **заменяет** ответ («Вы уже проходили этот опрос — можно изменить ответ»). Это защита от случайных дублей, не от злоумышленника.
7. Закрыт/удалён — «Опрос завершён» без деталей.
8. Лимит ответов на опрос: 200; rate limit отправки 10/мин на IP.
9. Антибот: honeypot-поле + минимальное время прохождения 15 сек.
10. **Ответов больше заявленного числа участников** — не блокируем. Сохраняем факт (`responses_over_declared`), показываем в админ-статистике. Решение, что с этим делать при реальной оплате, — после MVP.

### 5.5. Закрытие опроса и письмо руководителю

Опрос закрывается:
- вручную «Завершить опрос»;
- по сроку (фоновая задача раз в минуту);
- (опционально, чекбокс при создании, выкл. по умолчанию) — когда число ответов = заявленному числу участников.

При закрытии:
1. Статус `closed`, расчёт результатов в снимок `survey_result_snapshots` (JSON), чтобы отчёт был стабилен.
2. Письмо организатору: «Опрос „{название}“ команды „{команда}“ завершён: {N} ответов». В теле — сводка (ММ: топ-3 и анти-топ-3, при изменениях — самое болезненное изменение; HC: светофор таблицей + «обсудите в первую очередь») и кнопка «Открыть полный отчёт». При N = 0 — «Никто не ответил, можно продлить опрос».
3. Опрос можно **переоткрыть** (закрыт < 30 дней назад) — продлить срок; снимок пересчитается при следующем закрытии. Переоткрытие платного опроса повторной оплаты не требует.

### 5.6. Просмотр результатов

`/app/surveys/{id}`:
- Шапка: название, команда, статус, сроки, «ответили N из M», ссылка для участников, «Завершить» / «Переоткрыть».
- Пока опрос открыт — результаты видны в реальном времени (пересчёт на лету).
- Вкладки ММ: «Команда», «Влияние изменений» (если включено), «Участники» (только неанонимный), «Комментарии», «Обсуждение».
- Вкладки HC: «Светофор», «История», «Комментарии», «Обсуждение».
- Комментарии в анонимном режиме — в случайном порядке, без времени.

### 5.7. История

`/app/teams/{id}` — список опросов команды:
- **HC:** сетка «категория × волна» + график.
- **ММ:** сравнение двух опросов: сдвиг среднего ранга каждой карточки. Неанонимный — сдвиг по участнику при совпадении имени (без учёта регистра).

## 6. Анонимность и персональные данные

- **Порога анонимности нет**: сводные результаты анонимного опроса видны с первого ответа. Индивидуальные ответы анонимного опроса в UI и API организатора не отдаются никогда.
- В анонимном опросе **не храним** IP, user-agent, имя; `respondentKey` — только хеш (SHA-256 с солью опроса). Дата отправки — с точностью до дня.
- Логи приложения не содержат тел ответов и `respondentKey`. Для `/api/public/*` IP в логах не пишем.
- Неанонимный опрос: ПДн = имя + ответы, согласие участника фиксируется (флаг + версия + дата).
- Организатор — оператор ПДн своих сотрудников, сервис — обработчик по поручению. Оператор со стороны сервиса — ИП Варнавский В. Н. (реквизиты в конфиге `Legal:*`, выводятся в футере, на экране оплаты и в документах).
- Документы (рендерятся из markdown на страницах `/terms`, `/privacy`, `/consent`; плейсхолдеры реквизитов не нужны — тексты уже заполнены):
  - [docs/legal/offer.md](legal/offer.md) — публичная оферта (включая п. 4.4 «Период раннего доступа» — юридически закрывает имитацию оплаты);
  - [docs/legal/privacy.md](legal/privacy.md) — политика обработки ПДн;
  - [docs/legal/consent.md](legal/consent.md) — тексты чекбоксов согласия (организатор `org-1`, участник `part-1`) и плашка анонимного опроса.
- Каждый документ имеет номер редакции; при изменении — новая версия согласия.
- Удаление опроса/команды/аккаунта — физическое удаление ответов. Удаление аккаунта — из профиля, подтверждение по magic link.
- Почтовый провайдер — российский (Unisender Go, Яндекс 360 SMTP или аналог).

## 7. Монетизация: 299 ₽ за опрос (имитация оплаты в MVP)

### 7.1. Правило цены

- Опрос с **заявленным числом участников ≤ 8 — бесплатно**.
- **> 8 — 299 ₽ за опрос.** Оплата за каждый опрос, без подписок и пакетов.
- Порог и цена — в конфиге (`Pricing:FreeMaxParticipants = 8`, `Pricing:SurveyPriceRub = 299`).
- Цена фиксируется в опросе на момент создания (`price_rub`), чтобы изменение конфига не влияло на старые опросы.
- Расчёт — единый сервис `IPricingService.GetSurveyPrice(participants)`; на фронт цена приходит из API (`GET /api/pricing`), не хардкодится.

### 7.2. Имитация оплаты (fake door)

В MVP реальных платежей нет. Пользователь до последнего шага видит обычный путь оплаты, а в самом конце опрос запускается бесплатно. Цель — измерить, сколько людей готовы заплатить.

Путь для опроса > 8 участников:
1. В мастере кнопка «Перейти к оплате — 299 ₽» (вместо «Запустить»). Опрос сохраняется в статусе `draft` (ссылка ещё не работает).
2. Экран **«Оплата»** `/app/surveys/{id}/checkout`:
   - сводка: «{Тип опроса} · команда „{название}“ · {N} участников», сумма **299 ₽**;
   - выбор способа: «Банковская карта», «СБП», «SberPay» — **только радиокнопки, никаких полей ввода карты/телефона**, данные платёжных средств не запрашиваются и не собираются;
   - строка «Чек придёт на {email}» (email организатора, только отображение);
   - мелким текстом «ИП Варнавский В. Н., ИНН 352826429326» и ссылка на оферту;
   - кнопки «Оплатить 299 ₽» и «Назад».
3. Нажатие «Оплатить 299 ₽» → `POST /api/surveys/{id}/checkout` → сервер фиксирует событие `payment_clicked` (выбранный способ, сумма), переводит опрос в `open` → экран:
   > **Опрос запущен — бесплатно 🎉**
   > Сейчас сервис работает в режиме раннего доступа, оплата не списывается. Спасибо, что готовы поддержать проект!

   и дальше — обычный экран «Опрос запущен» (ссылка, QR, текст приглашения).
4. Ни на одном шаге не показываем «оплачено», не отправляем чек и письмо об оплате — ничего, что выглядит как подтверждение реального платежа.
5. Если пользователь ушёл с экрана оплаты — опрос остаётся `draft`. В списке опросов: «Черновик — ожидает оплаты» с кнопкой «Перейти к оплате». Черновики старше 30 дней удаляются фоновой задачей.

### 7.3. Метрики гипотезы

Таблица `funnel_events` (см. §9), события:
- `survey_draft_paid_required` — создан опрос > 8 участников;
- `checkout_viewed` — открыт экран оплаты;
- `payment_method_selected` — выбран способ (с `method`);
- `payment_clicked` — нажал «Оплатить»;
- `checkout_abandoned` — вычисляемое: был `checkout_viewed`, нет `payment_clicked` за 24 ч.

В админке (`/admin`) — воронка за период: создано опросов ≤ 8 / > 8, дошли до оплаты, нажали «Оплатить», конверсия, распределение по способу оплаты и по размеру команды.

### 7.4. Реальная оплата (после MVP)

- ЮKassa на **ИП**, способы: карта, СБП, SberPay. Чеки 54-ФЗ — «Чеки от ЮKassa».
- `POST /api/surveys/{id}/checkout` вместо запуска опроса создаёт платёж и возвращает `confirmationUrl`; webhook `payment.succeeded` → опрос `open`. Идемпотентность по `payment.id`.
- Для юрлиц — счёт по запросу.
- Архитектура MVP должна это позволять без переделки: шаг `draft → checkout → open` уже есть, меняется только реализация `ICheckoutService` (`FakeCheckoutService` → `YooKassaCheckoutService`), выбор — по конфигу `Pricing:CheckoutMode = fake|yookassa`.

## 8. Архитектура и технологии

### 8.1. Стек

- **Backend:** .NET 10 (LTS), ASP.NET Core Web API (контроллеры), EF Core 10 + Npgsql, FluentValidation, Serilog.
- **БД:** PostgreSQL 17. Миграции EF Core. `jsonb` для ответов и снимков.

### 8.2. Деплой: Coolify

- Сервер: VPS **Timeweb Cloud** (ДЦ в РФ) с установленным Coolify. DNS `movingmotivators.ru` и `www` → IP VPS; `www` редиректит на корень. S3 для бэкапов — Timeweb Cloud S3. Coolify управляет Traefik, выдаёт SSL (Let's Encrypt), хранит env-переменные, делает деплой из Git по push.
- **Ресурсы в Coolify:**
  1. **PostgreSQL** — как отдельный Database-ресурс Coolify. Включить Scheduled Backups (ежедневно, хранение 14 дней) в Timeweb Cloud S3.
  2. **Приложение** — Docker Compose build pack из репозитория, файл `docker-compose.yml` (prod):
     - `api` — `backend/Dockerfile` (multi-stage, `mcr.microsoft.com/dotnet/aspnet:10.0`), слушает 8080, health-check `/health`;
     - `web` — `frontend/Dockerfile` (multi-stage: node build → nginx:alpine), отдаёт статику и проксирует `/api` в `api:8080`. Домен назначается сервису `web` в Coolify. Один домен — без CORS.
- Строка подключения к БД, SMTP, `App:BaseUrl`, `App:AdminEmails`, реквизиты ИП, `Pricing:*` — через env в Coolify. Секретов в репозитории нет; `.env.example` с перечнем всех переменных.
- **Миграции:** применяются при старте `api` (`Database.Migrate()` за флагом `Db:MigrateOnStartup=true`), один инстанс api — гонок нет.
- `docker-compose.dev.yml` для локальной разработки: postgres, mailpit, api, web (или запуск `dotnet run` + `vite` с прокси).
- Логи — stdout (JSON), смотрятся в Coolify.

## 9. Модель данных (PostgreSQL)

Все `id` — `uuid` (UUIDv7), время — `timestamptz` в UTC.

**users**
- `id`, `email` (citext, unique), `display_name` null, `email_verified_at` null, `created_at`, `last_login_at`, `consent_version` null, `consent_at` null.

**login_tokens**
- `id`, `user_id` FK, `token_hash` (bytea, unique), `purpose` (`login`, `delete_account`), `expires_at`, `used_at` null, `created_at`, `return_url` null.

**sessions**
- `id`, `user_id` FK, `session_hash` (bytea, unique), `created_at`, `expires_at`, `last_seen_at`.

**teams**
- `id`, `owner_id` FK users, `name`, `size` (int), `archived_at` null, `created_at`.

**surveys**
- `id`, `team_id` FK, `type` (`moving_motivators`, `health_check`), `methodology_version` (int), `title`, `is_anonymous` (bool), `declared_participants` (int), `price_rub` (int, 0 = бесплатно), `public_code` (varchar(16), unique), `welcome_message` null, `settings` jsonb, `auto_close_on_full` bool, `status` (`draft`, `open`, `closed`), `opened_at` null, `closes_at` null, `closed_at` null, `created_at`.
- `settings` ММ: `{ changes: [{ id: "c1", text: string }] }` — пустой массив = шаг влияния выключен; `id` стабилен, не меняется при правке текста. HC: `{ categories: string[] }`.
- Индексы: `(team_id, created_at desc)`, `(status, closes_at)`.

**responses**
- `id`, `survey_id` FK (on delete cascade), `respondent_key_hash` (bytea), `participant_name` null, `payload` jsonb, `comment` null, `submitted_on` (date), `submitted_at` null (только неанонимные), `consent_version` null, `updated_count` int default 0.
- Unique `(survey_id, respondent_key_hash)`.
- `payload` ММ: `{ ranking: [10 ключей, последний = самый важный], ratings: { "freedom": 1..5, …все 10 } (с версии методики 2), impact: { "c1": { "freedom": 1|0|-1, …все 10 }, … } | null }`.
- `payload` HC: `{ answers: { "delivery": { score: 1..3, trend: -1|0|1, comment: string|null }, … } }`.

**survey_result_snapshots**
- `survey_id` PK/FK, `computed_at`, `response_count`, `result` jsonb (тот же DTO, что API результатов).

**checkouts**
- `id`, `survey_id` FK, `user_id` FK, `amount_rub`, `method` null (`card`, `sbp`, `sberpay`), `mode` (`fake`, `yookassa`), `status` (`created`, `clicked`, `succeeded`, `canceled`), `provider_payment_id` null unique, `created_at`, `clicked_at` null.

**funnel_events**
- `id`, `user_id` FK, `survey_id` null, `event` (varchar), `props` jsonb, `at`.

**audit_log**
- `id`, `user_id` null, `action`, `entity`, `entity_id`, `at` — вход, создание/удаление команд и опросов, checkout, удаление аккаунта.

| POST | `/public/surveys/{code}/responses` | `{ respondentKey, participantName?, payload, comment?, consent?, honeypot, startedAt }` → 201 / 200 (замена) |
| POST | `/public/surveys/{code}/responses/mine` | `{ respondentKey }` → свой ответ (ключ в теле, не в query) |

Валидация payload строго по методике: ММ — ровно 10 уникальных ключей каталога; `ratings` — с версии методики 2 обязательно, ровно 10 ключей, значения 1..5, в версии 1 недопустимо; `impact` — только если `changes` не пуст, ровно набор `id` изменений, в каждом ровно 10 ключей, значения {-1,0,1}. HC — ровно включённые категории, score ∈ {1,2,3}, trend ∈ {-1,0,1}.
